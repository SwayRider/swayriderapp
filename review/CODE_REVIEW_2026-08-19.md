### 1. ~~Auth/refresh tokens stored in plaintext via `shared_preferences`, not secure storage~~ — FIXED 2026-08-19

`lib/data/services/shared_preferences_service.dart:1-67`. `AuthRepositoryRemote._saveTokens` (`lib/data/repositories/auth/auth_repository_remote.dart:260-267`) persists access and refresh tokens with `SharedPreferences.setString`. No `flutter_secure_storage` (or equivalent Keychain/Keystore-backed) dependency exists anywhere in `pubspec.yaml`. On Android, `SharedPreferences` backs onto an unencrypted XML file under the app's data dir; on a rooted device, via `adb backup`, or through any file-read primitive (another vuln, a malicious accessibility-service app, USB debugging), the long-lived refresh token can be exfiltrated and used to mint new sessions indefinitely. Severity: High.

Replaced `SharedPreferencesService` with `SecureTokenStorageService` (`lib/data/services/secure_token_storage_service.dart`), backed by `flutter_secure_storage` (Keychain on iOS with `first_unlock` accessibility, encrypted Keystore-backed storage on Android) instead of a plaintext preferences file. Renamed the class rather than swapping the backend in place, since a storage class named after the old, less-sensitive backend would itself be a landmine for future audits. Updated all call sites (`auth_repository_remote.dart`, `config/dependencies.dart`, `config/app_config.dart` doc comments, `CLAUDE.md`) and test mocks (`test/helpers/mocks.dart`, `auth_repository_remote_test.dart`, `router_test.dart`). Added `test/data/services/secure_token_storage_service_test.dart` (9 tests, replacing the deleted `shared_preferences_service_test.dart`, plus one new case for a throwing storage read). `pubspec.yaml`: `shared_preferences` removed, `flutter_secure_storage: ^11.0.0` added. No migration code — per product decision, already-logged-in users are logged out and must sign in again after this ships; old plaintext entries are simply never read by the new code path. `flutter analyze` and the full `flutter test` suite (218 tests) pass. Committed on branch `fix/secure-token-storage`.

Known follow-up, not addressed by this fix: unlike the old `SharedPreferences` (wiped on uninstall), iOS Keychain persists across uninstall/reinstall by default — a reinstall on the same device could silently restore a still-valid token unless the backend independently expires/rotates refresh tokens. Worth raising with the team separately.

### 2. Tokens logged in plaintext via freezed `toString()` interpolation

`lib/data/repositories/auth/auth_repository_remote.dart:98,246,254`: `_log.fine('[DIAG] ... resolved with $result')` interpolates the full `Result<RefreshResponse>`/retry result. `RefreshResponse`/`LoginResponse` (`lib/data/services/api/model/auth/refresh_response.dart`, `login_response.dart`) are `@freezed` with default-generated `toString()`, which dumps `accessToken`/`refreshToken` as plain fields — so these log lines contain raw live session tokens. `Logger.root` currently has no `onRecord` listener anywhere in the codebase (checked `main.dart`, `main_development.dart`, `dependencies.dart`), so nothing is actually written to console/disk today — but this is a fragile accident, not a control. The moment a listener is wired up (console printer, file sink, or crash/log aggregation service — a near-certainty before release), every login/refresh emits full tokens to that sink. These `[DIAG]`-tagged lines (also in `router.dart:135-171`, `auth_api_client.dart:167,170`) read as leftover debug instrumentation that should be removed or scrubbed before it becomes a real leak. Severity: Medium.

### 3. Local loopback proxy forwards authenticated requests for arbitrary paths, not just tiles

`lib/data/repositories/tiles/tiles_repository_remote.dart:86-124`. `_handleRequest` only pattern-matches the tile path (`_tilePathRegExp`); anything that doesn't match falls through to `_forward`, which attaches the live bearer token and proxies to the real tiles backend regardless of path/method. The server binds to `InternetAddress.loopbackIPv4` on an OS-assigned port, which is reasonable containment, but Android does not sandbox loopback per-app — another app on the same device with `INTERNET` permission can port-scan `127.0.0.1` and, if it finds the proxy while it's running (during an active map session), relay arbitrary requests to the tiles API using the victim's token. Scoping `_handleRequest` to only forward requests matching `_tilePathRegExp` (rejecting everything else with 404) would close this off cheaply. Severity: Medium.

### 4. PII (email addresses) in `fine`-level logs

E.g. `auth_repository_remote.dart:70` (`'Logging in as $email'`), `:141,156,173` log email addresses. Same caveat as #2: currently inert (no listener), but should not ship as-is once logging is wired to a real sink — pair with the fix for #2 rather than treating separately. Severity: Low.
